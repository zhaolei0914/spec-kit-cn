## 🎯 核心设计理念

### 三层上下文加载模型

```
┌─────────────────────────────────────────────┐
│ L1: 全局上下文 (所有阶段必读)               │
│     SKILL.md + Wiki Overview.md             │
├─────────────────────────────────────────────┤
│ L2: 角色上下文 (按角色加载)                 │
│     BA → Templates | Architect → CLI-Core  │
│     Developer → Memory | QA → Documentation │
├─────────────────────────────────────────────┤
│ L3: 任务上下文 (按需加载)                   │
│     需求摘要 | 设计决策 | 代码模式 | 测试策略│
└─────────────────────────────────────────────┘
```

### 三大原则

1. **最小必要原则**: 只加载当前阶段需要的上下文
2. **渐进增强原则**: 从全局 → 角色 → 任务，逐层细化
3. **一致性原则**: 所有阶段从同一套 Skill/Wiki 加载

## 💡 预期效果

### ✅ 需求分析阶段（/1）

**Before**:
- LLM 不了解项目架构边界
- 需求文档结构不统一
- 不参考历史需求

**After**:
- ✅ 理解项目架构边界，不提出超出能力的需求
- ✅ 需求文档结构符合 Wiki Templates 规范
- ✅ 自动参考归档需求的 FR 结构

### ✅ 开发设计阶段（/3）

**Before**:
- 设计方案与项目架构不一致
- 重复踩坑，不参考历史决策
- 不复用现有代码模式

**After**:
- ✅ 设计方案符合 Wiki Overview 的架构模式
- ✅ 复用 Memory 中的历史设计决策
- ✅ 避免重复踩坑

### ✅ 编写代码阶段（/6）- 最关键！

**Before**:
- 代码不符合 SKILL.md 规范（使用 `print()` 而非 `console.print()`）
- 接口定义与 Design.md 不一致
- 重复实现已存在的函数
- 重复踩已知陷阱

**After**:
- ✅ **100% 符合 SKILL.md 规范**：命名、格式、禁止规则
- ✅ **100% 符合 Design.md 接口**：函数签名、参数、返回值
- ✅ **优先复用现有代码**：减少重复实现
- ✅ **避免已知陷阱**：参考 Known-Pitfalls

### ✅ 测试验证阶段（/8, /9）

**Before**:
- 测试用例与需求规范脱节
- 测试策略不统一

**After**:
- ✅ 测试用例直接从 Spec.md 的 GWT 场景生成
- ✅ 测试策略符合 Memory 规范

## 🎉 总结

通过将 **Skill**（规范）、**Wiki**（架构）、**Memory**（经验）深度集成到 Harness 11 步工作流，我们实现了：

### 核心价值

1. **规范统一**: 所有阶段从同一套 Skill/Wiki 加载
2. **上下文精准**: 每个角色只加载需要的上下文
3. **质量保障**: LLM 严格遵守规范和接口定义
4. **知识复用**: 自动参考历史决策和代码模式
5. **避免踩坑**: 参考已知陷阱，减少重复错误

### 最终目标

**让 LLM 在 Harness 工作流的每个阶段都能获取正确的上下文，写出符合业务和规范的高质量代码！**

---

**Skill 是规范之手，Wiki 是架构之眼，Memory 是经验之库，三者协同指导 LLM！** 🚀
