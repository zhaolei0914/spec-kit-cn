# 项目上下文 Skill 设计方案

> 版本: 1.1 | 日期: 2026-04-02 | Phase 1 已实现
>
> 目标：设计一套完整的项目上下文生成方案，让 LLM 真正理解项目全局——技术栈、结构、方案、规范、环境，而非仅仅看懂孤立的代码片段。

---

## 一、问题分析

### 1.1 核心问题

LLM 在项目开发中面临的根本挑战是**上下文缺失**：

- 看到一段代码，不知道它属于什么项目、用什么技术栈
- 不了解目录结构和模块关系，改一处不知道会影响哪里
- 不清楚业务流程，只能做语法层面的修改
- 不知道团队规范，写出的代码风格不统一
- 不了解运行环境，输出的代码无法直接落地

用 Anthropic 的比喻：**代码片段是「树叶」，项目上下文是「整棵大树」**。没有大树的全局信息，LLM 永远只能做"片叶级"的代码补全。

### 1.2 现有方案的差距

| 维度 | 理想状态 | Phase 1 实现后 | 差距 |
|------|----------|---------------|------|
| **技术栈** | 语言、框架、中间件、版本 | ✅ 自动检测语言占比和依赖 | 框架检测仍需 LLM 补充 |
| **项目结构** | 架构类型、目录规范、模块关系 | ✅ 目录树 + 知识图谱 + **架构类型自动检测** | 架构描述需 LLM 补充 |
| **技术方案** | 业务流程、设计模式、核心规则 | ⚠️ 入口点 + 执行流 | 业务语义仍需 LLM 推理 |
| **开发规范** | 命名、风格、禁止规则 | ✅ **CodePatternDetector 自动检测命名/缩进/docstring/import/反模式** | LLM 仅需补充遗漏 |
| **环境配置** | 配置文件、环境变量、部署方式 | ✅ 配置文件 + **代码中环境变量自动扫描** | 部署方式需 LLM 描述 |

**Phase 1 成果：开发规范和环境配置两个维度已从"纯占位符"升级为"自动检测 + LLM 补充"。技术方案仍需 LLM 推理。**

## 二、业界调研

### 2.1 上下文工程的核心理念

来自 Anthropic《Effective Context Engineering for AI Agents》（2025）的关键洞见：

> **上下文工程 ≠ 提示工程。** 提示工程关注如何写好指令；上下文工程关注如何策展和维护推理时的最优 token 集合——包括系统指令、工具、外部数据、消息历史等所有信息。

核心原则：

1. **注意力预算有限** — LLM 的上下文窗口存在「上下文腐烂」(context rot)：token 越多，检索精度越低。必须精心策展，用最少的高信号 token 最大化效果。
2. **分层加载** — 不要一次性灌入所有信息。热记忆（always loaded）+ 冷记忆（on-demand retrieval）的混合策略最有效。
3. **为机器而写** — 上下文文档的读者是 AI agent，不是人类开发者。要用文件路径、函数名、明确的"做什么/不做什么"格式。
4. **实时性** — 静态文档会过时（specification staleness），需要检测漂移并及时更新。

### 2.2 业界方案对比

| 方案 | 核心思路 | 优势 | 劣势 |
|------|----------|------|------|
| **CLAUDE.md / .cursorrules** | 手写项目规则文件，每次会话自动加载 | 简单直接，热加载 | 纯手工维护，易过时 |
| **Claude /init** | LLM 扫描项目文件自动生成 CLAUDE.md | 自动化起步 | 只捕获显性模式，错过业务逻辑 |
| **Aider repo-map** | tree-sitter 解析 + 图排序，生成代码地图 | 精确的符号级上下文 | 仅代码结构，无业务/规范 |
| **GitNexus** | 知识图谱（符号、调用链、聚类、执行流） | 深度代码分析 | 输出是符号索引，非项目理解 |
| **Repomix / repo2txt** | 打包整个仓库为文本 | 完整性好 | token 爆炸，无提炼 |
| **llms.txt** | 标准化的 AI 友好文档入口 | 标准格式，渐进式 | 需手动编写 |
| **Codified Context (论文)** | 三层架构：宪法 + 专家 Agent + 知识库 | 学术最优，大型项目验证 | 维护成本高（~1-2h/周） |

### 2.3 关键启发

**从 Anthropic 上下文工程指南：**
- 用 XML 标签或 Markdown 标题分隔上下文的不同部分
- 提供规范的示例（few-shot），而非穷举边界条件
- 工具返回的信息要 token 高效

**从 Codified Context 论文（2602.20478）：**
- **三层架构**：热记忆（宪法，~660行，always loaded）→ 领域专家（agents，按需调用）→ 冷知识库（subsystem docs，检索加载）
- **为 AI 而写**：文件路径 + 参数名 + 期望行为 + "做/不做"指令
- **活文档**：AI 自己生成和更新规范文档，开发者审核
- **漂移检测**：解析 git commit，检查规范是否与代码脱节

**从 Addy Osmani 工作流：**
- Skills 的价值：把脆弱的重复提示变成持久可复用的封装
- 上下文打包：用工具自动化，但关键部分仍需人工指导
- "brain dump" 原则：高层目标、不变量、好的示例、要避免的方法

**从 Claude Code 最佳实践：**
- CLAUDE.md 分层：全局 → 项目根 → 子目录，按需加载
- 给 Claude 一张「地图」：项目摘要 + 目录结构 + 关键依赖
- 连接工具：记录自定义工具的用法
- 定义标准工作流：常见操作的步骤化指令

## 三、设计方案

### 3.1 核心设计理念

```
项目上下文 = 工具自动提取（事实层） + LLM 推理生成（理解层） + 人工审核（校验层）
```

**关键创新点：不是让工具生成最终文档，而是让工具提供"原材料"，由 LLM 在工作流中推理生成完整上下文。**

这解决了现有方案的根本矛盾：
- 纯工具（GitNexus、tree-sitter）：能精确提取代码事实，但无法理解业务语义
- 纯 LLM：能理解语义，但没有结构化数据支撑容易幻觉
- **工具 + LLM 协同**：工具提供事实基础，LLM 在事实之上推理出语义理解

### 3.2 三阶段流水线

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  阶段 1：采集    │ ──▶ │  阶段 2：推理    │ ──▶ │  阶段 3：输出    │
│  (工具自动化)    │     │  (LLM 填充)     │     │  (结构化 Skill)  │
└─────────────────┘     └─────────────────┘     └─────────────────┘
     │                        │                        │
     ├─ 项目文件扫描           ├─ 读取采集数据           ├─ SKILL.md (热加载)
     ├─ GitNexus 知识图谱      ├─ 抽样读取关键代码       ├─ 模块详情 (按需)
     ├─ 依赖解析              ├─ 推理填充占位符          └─ index.yaml (索引)
     ├─ 配置文件解析           └─ 生成自然语言描述
     └─ 代码模式检测
```

### 3.3 阶段 1：自动采集（工具层）

#### 3.3.1 数据源矩阵

| 数据源 | 提取内容 | 工具 | 输出 |
|--------|----------|------|------|
| **包管理文件** | 语言、依赖、版本 | Python 脚本 | 技术栈事实 |
| **配置文件** | 构建工具、CI/CD、容器化 | Python 脚本 | 工具链事实 |
| **目录结构** | 目录树、文件统计 | Python 脚本 | 结构事实 |
| **GitNexus 图谱** | 模块聚类、执行流、依赖 | GitNexus Docker | 代码关系事实 |
| **代码抽样** | 代码风格、命名模式 | Python 脚本 | 规范线索 |
| **环境文件** | 环境变量、配置项 | Python 脚本 | 环境事实 |
| **README/文档** | 项目描述、架构说明 | 文件读取 | 文档事实 |

#### 3.3.2 新增：代码模式检测器

现有扫描器缺少对代码本身模式的检测。需要新增一个轻量级检测器，从代码中提取：

```python
# 代码模式检测器（不依赖 tree-sitter，用正则 + 启发式）
class CodePatternDetector:
    """扫描代码文件，提取命名约定、代码风格、常用模式"""

    def detect_naming_convention(self, files):
        """检测函数/变量命名风格: snake_case / camelCase / PascalCase"""

    def detect_indentation(self, files):
        """检测缩进方式: 空格(2/4) / Tab"""

    def detect_import_patterns(self, files):
        """检测导入模式: 绝对/相对导入, 导入分组"""

    def detect_error_handling(self, files):
        """检测异常处理模式: try/except 风格, 异常类型"""

    def detect_docstring_style(self, files):
        """检测文档字符串风格: Google / NumPy / Sphinx / 无"""

    def detect_anti_patterns(self, files):
        """检测反模式: print 调试, 裸 except, 硬编码, import *"""

    def detect_architecture_hints(self, files):
        """检测架构线索: MVC/MVVM 模式, 分层结构, 微服务信号"""
```

### 3.4 阶段 2：LLM 推理填充

**这是关键创新**。阶段 1 生成带 `{{LLM_*}}` 占位符的骨架文档 + 结构化事实数据，阶段 2 由 LLM 在工作流中完成推理填充。

#### 3.4.1 LLM 推理策略

LLM 需要完成的推理任务及其策略：

| 占位符 | 推理任务 | 输入数据 | 策略 |
|--------|----------|----------|------|
| `{{LLM_ARCHITECTURE}}` | 判断整体架构类型 | 目录结构 + 模块聚类 + 包信息 | 模式匹配 + 推理 |
| `{{LLM_BUSINESS_FLOWS}}` | 描述核心业务流程 | 入口点 + 执行流 + 关键函数 | 抽样读代码 + 推理 |
| `{{LLM_DESIGN_PATTERNS}}` | 识别设计模式 | 类名模式 + 继承关系 + 代码结构 | 启发式 + 推理 |
| `{{LLM_NAMING_CONVENTIONS}}` | 提炼命名规范 | 代码模式检测结果 | 统计 + 归纳 |
| `{{LLM_CODE_STYLE}}` | 提炼代码风格 | 缩进 + docstring + import 模式 | 统计 + 归纳 |
| `{{LLM_FORBIDDEN_RULES}}` | 列出禁止规则 | 反模式检测 + 代码审查 | 推理 + 最佳实践 |
| `{{LLM_ENV_VARIABLES}}` | 列出环境变量 | .env 文件 + 代码中的 getenv | 扫描 + 脱敏 |
| `{{LLM_DEPLOYMENT}}` | 描述部署方式 | Dockerfile + CI 配置 + 脚本 | 读文件 + 推理 |
| `{{LLM_FRAMEWORKS}}` | 补充框架信息 | 依赖列表 + import 分析 | 推理 |

#### 3.4.2 LLM 推理工作流

在 `0-制定项目上下文.md` 的阶段 2 中，LLM 执行以下步骤：

```
步骤 2.1：读取采集数据
  → 加载 project-context-facts.json（阶段 1 输出的事实数据）
  → 加载 SKILL.md 骨架文档

步骤 2.2：抽样读取关键代码
  → 根据入口点列表，读取 top 5 入口文件的关键函数
  → 根据 README 和现有文档，获取项目描述

步骤 2.3：逐个填充占位符
  → 对每个 {{LLM_*}} 占位符：
     1. 读取占位符后的 <!-- 填充指导 --> 注释
     2. 结合事实数据 + 代码样本进行推理
     3. 生成简洁、准确、面向 AI 的描述
     4. 替换占位符

步骤 2.4：质量自检
  → 检查是否还有未填充的占位符
  → 检查生成内容是否与事实数据一致
  → 检查 token 预算（SKILL.md 应控制在 ~500 行以内）
```

#### 3.4.3 填充指导设计原则

每个占位符的填充指导遵循以下原则（来自 Anthropic 的建议）：

1. **为 AI 而写**：使用文件路径、函数名、具体参数，而非模糊描述
2. **做/不做格式**：明确列出要做什么、不做什么
3. **简洁高信号**：每条规范 1-2 行，避免长篇大论
4. **可操作**：每条规范都能直接指导编码行为

示例（好的填充）：
```markdown
### 命名规范

- **函数/变量**: `snake_case` — 如 `extract_all()`, `skill_path`
- **类名**: `PascalCase` — 如 `KnowledgeExtractor`, `ApiEndpoint`
- **常量**: `UPPER_SNAKE_CASE` — 如 `AGENT_CONFIG`, `EXT_LANG_MAP`
- **文件名**: `snake_case.py` — 如 `skill_generator.py`, `api_extractor.py`
- **CLI 命令**: `kebab-case` — 如 `specify-cn`, `cursor-agent`
```

示例（差的填充）：
```markdown
### 命名规范

本项目使用 Python 编程语言，因此遵循 PEP 8 命名规范。变量和函数使用小写字母
加下划线的方式命名（snake_case），类名使用首字母大写的驼峰命名法（PascalCase）。
这些规范有助于保持代码的一致性和可读性...（冗长、无具体示例、浪费 token）
```

#### 3.5.3 Token 预算控制

根据 Anthropic 的「注意力预算」理念，SKILL.md 需要严格控制体积：

| 层级 | 文件 | 目标行数 | 加载策略 |
|------|------|----------|----------|
| **Tier 1 热加载** | SKILL.md | 300-500 行 | 每次会话自动加载 |
| **Tier 2 按需** | modules/*.md | 各 50-100 行 | 修改该模块时加载 |
| **Tier 3 存档** | .context-facts.json | 不限 | 仅更新时使用 |

超过 500 行的 SKILL.md 会导致「上下文腐烂」，降低 LLM 的关注精度。

### 3.6 增量更新与漂移检测

#### 3.6.1 漂移检测机制

参考 Codified Context 论文的 drift detector 思路：

```
当代码发生变更时：
1. 解析 git diff，识别变更的文件
2. 查找受影响的模块（通过 index.yaml 的文件→模块映射）
3. 对比 .context-facts.json 中的事实数据与当前代码状态
4. 如果检测到显著漂移 → 提示用户重新运行项目上下文生成
```

#### 3.6.2 增量更新策略

- **轻量更新**（代码变更少）：仅更新受影响的模块 Skill
- **全量重建**（架构变更大）：重新运行完整流水线
- **触发条件**：可在 `0-制定项目上下文` 工作流开始时自动检查

## 五、与现有工具的协同

### 5.1 数据流

```
                    ┌──────────────┐
                    │  项目代码库    │
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
      ┌──────────┐  ┌──────────┐  ┌──────────┐
      │ 项目扫描器 │  │ GitNexus │  │ 代码模式  │
      │(文件/依赖) │  │(知识图谱) │  │ 检测器   │
      └─────┬────┘  └─────┬────┘  └─────┬────┘
            │              │              │
            ▼              ▼              ▼
      ┌────────────────────────────────────────┐
      │         .context-facts.json            │
      │  (结构化事实数据 — 工具层输出)            │
      └────────────────────┬───────────────────┘
                           │
                           ▼
      ┌────────────────────────────────────────┐
      │     SKILL.md 骨架 (带 {{LLM_*}} 占位符) │
      │  (阶段 1 输出 — 工具可确定的部分已填充)    │
      └────────────────────┬───────────────────┘
                           │
                           ▼
      ┌────────────────────────────────────────┐
      │          LLM 推理填充                   │
      │  (阶段 2 — 读取事实 + 抽样代码 → 填充)    │
      └────────────────────┬───────────────────┘
                           │
                           ▼
      ┌────────────────────────────────────────┐
      │        完整的项目上下文 SKILL.md          │
      │  (五大维度全部填充，可直接使用)             │
      └────────────────────────────────────────┘
```

### 5.2 工具职责划分

| 工具 | 职责 | 输出 |
|------|------|------|
| **gitnexus_to_skill.py** | 阶段 1：采集事实 + 生成骨架 | `.context-facts.json` + `SKILL.md`(骨架) |
| **0-制定项目上下文.md** | 阶段 2：编排 LLM 推理填充 | `SKILL.md`(完整) |
| **GitNexus Docker** | 代码知识图谱构建 | `.claude/skills/generated/` |
| **漂移检测器**（新增） | 检测上下文过期 | 漂移报告 |

### 5.3 无 GitNexus 时的降级方案

当 Docker 不可用或 GitNexus 镜像未构建时：

- 项目扫描器 + 代码模式检测器仍可工作
- 缺少知识图谱数据（模块聚类、执行流、依赖关系）
- LLM 需要更多自主探索来补充模块结构信息
- SKILL.md 的"模块划分"和"执行流"部分改为 LLM 填充

## 六、质量评估标准

一个「完美」的项目上下文 Skill 应通过以下检验：

### 6.1 完整性检验

- [ ] LLM 读完 SKILL.md 后，能正确回答"这个项目用什么技术栈？"
- [ ] LLM 能判断一段代码应该放在哪个目录
- [ ] LLM 能描述修改某文件可能影响的其他模块
- [ ] LLM 写出的新代码符合项目的命名规范和代码风格
- [ ] LLM 不会违反项目的禁止规则

### 6.2 精简性检验

- [ ] SKILL.md 不超过 500 行
- [ ] 没有冗余/重复的信息
- [ ] 每条信息都能直接指导编码行为
- [ ] 无需阅读其他文档即可理解项目全局

### 6.3 准确性检验

- [ ] 技术栈信息与实际依赖一致
- [ ] 目录结构与实际目录一致
- [ ] 模块关系与代码调用关系一致
- [ ] 命名规范与现有代码一致
- [ ] 无幻觉内容（所有事实可溯源）

### 6.4 可维护性检验

- [ ] 支持增量更新，不需要每次全量重建
- [ ] 有漂移检测机制，能发现上下文过期
- [ ] 人工审核成本低（<10 分钟/次）

## 七、总结

### 核心观点

1. **项目上下文不是代码索引**。GitNexus 的符号图谱是好的"原材料"，但不是最终产品。LLM 需要的是"理解"而非"索引"。

2. **工具 + LLM 协同是最优解**。纯工具无法理解业务语义，纯 LLM 容易幻觉。让工具提供事实基础，LLM 在事实之上推理。

3. **分层加载是必要的**。500 行的热加载 SKILL.md + 按需加载的模块详情，比 2000 行的巨型文档效果好得多。

4. **为 AI 而写**。项目上下文的读者是 LLM，不是人类开发者。文件路径、函数名、做/不做规则，这些具体信号远比散文描述有效。

5. **活文档必须有维护机制**。漂移检测 + 增量更新，否则过时的上下文比没有上下文更危险。

### 一句话

> **完美的项目上下文 = 工具提取事实骨架 + LLM 推理填充语义 + 分层策展控制 token 预算 + 漂移检测保持实时性**
