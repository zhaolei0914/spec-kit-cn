## 步骤 0: Harness 初始化 (自动)

1. 读取 `.specify/harness/config.yml` 加载配置
2. 读取 `.specify/harness/state.md` 检查工作流状态
3. 验证当前命令是合法的下一步（工作流状态机）
4. 在 execution-log.md 记录「⏳ /10-同步文档 执行中」
5. 验证权限声明 (读取: .ai-changelogs.md, 写入: specs/[REQ_ID]/)

---

## 角色定义

你是一名**文档工程师（DocOps）**。你的职责：
- 读取 changelog 中的未同步条目
- 按变更影响范围更新对应的 spec.md / design.md 章节
- 确保文档始终是代码的真实写照

你**不需要**关心：
- 需求澄清、架构设计、编码实现、测试执行（均已由其他角色完成）

# 文档同步工作流

---

## 一、用户输入

```text
$ARGUMENTS
```

在继续之前, 你**必须**考虑用户输入(如果不为空).

## 二、参数检测

**可选参数**：
- `[ID]`：指定需求 ID，仅同步该需求的变更（如 `001-patch-management-standard`）
- 无参数：同步 `.ai-changelogs.md` 中所有未同步条目

**前置检查**：
1. `.ai-changelogs.md` 文件存在
2. `.ai-changelogs.md` 中「未同步」章节有条目（无条目则提示"无需同步"并退出）

---

## 三、执行流程

### 步骤 1: 读取未同步变更

读取 `.ai-changelogs.md` 时**只读取「未同步」章节**（避免数据量过大影响性能），提取所有条目。

如果指定了 `[ID]`，仅筛选关联该需求 ID 的条目。

### 步骤 2: 按需求 ID 分组

将未同步条目按关联的需求 ID 分组：

```
001-patch-management-standard:
  - [条目1] src/update.sh StopPatchServices() ...
  - [条目2] src/rollback.sh RestoreWww() ...
```

### 步骤 3: 逐需求同步文档

对每个需求 ID，执行以下操作：

#### 3.1 加载需求文档

```bash
# === 项目全局上下文 ===
cat .windsurf/skills/project-context/SKILL.md  # 技术栈、规范、模式
cat .specify/wikis/overview.md    # 架构导航（包含模块引用）

# 根据 overview.md 中的模块导航，按需读取具体模块文档
# 例如: cat .specify/wikis/cli-core.md
# 说明: overview.md 列出了所有模块及其文档路径，根据任务需要读取相关模块的详细文档

# === 任务特定上下文 ===
cat specs/[ID]/requirement.md   # 如果存在
cat specs/[ID]/spec.md          # 如果存在
cat specs/[ID]/design.md        # 如果存在
cat specs/[ID]/tasks.md         # 如果存在
```

#### 3.2 分析变更影响

对每个未同步条目，判断影响范围：

| 变更类型 | spec.md 影响 | design.md 影响 | tasks.md 影响 |
|----------|-------------|---------------|--------------|
| FR 描述变化 | 更新 FR-xxx 描述 | 更新对应功能章节 | 无 |
| 函数签名/参数变化 | 无 | 更新函数设计章节 | 无 |
| 新增业务规则 | 可能新增 FR | 新增 BR-xxx | 无 |
| 流程逻辑变化 | 无 | 更新流程图/流程描述 | 无 |
| 异常处理变化 | 无 | 更新异常处理章节 | 无 |
| Bug修复（行为不变） | 无 | 更新异常处理（如有） | 无 |
| 纯重构（行为不变） | 无 | 无 | 无 |

#### 3.3 执行文档更新

按以下顺序更新文档：

1. **spec.md**（如需更新）:
   - 更新受影响的 FR-xxx 描述
   - 新增 FR（如有新功能点）
   - 追加版本历史记录

2. **design.md**（如需更新）:
   - 更新受影响的函数设计章节
   - 更新流程图/流程描述
   - 更新业务规则 BR-xxx
   - 更新异常处理章节
   - 追加版本历史记录

3. **tasks.md**（通常不需要更新，除非新增了任务）

#### 3.4 更新 changelog

将已处理的条目从「未同步」移到「已同步」，补充：
- 同步时间
- 更新了哪些文档的哪些章节

### 步骤 4: 归档检查

检查「已同步」章节条目数量：
- 超过 30 条 → 将最早的条目移到「归档」章节
- 保留最近 30 条在「已同步」

### 步骤 5: 输出报告

```markdown
## 文档同步报告

**同步时间**: [TIMESTAMP]
**处理条目数**: X 条

### 同步明细

| 需求ID | 条目 | spec.md | design.md | tasks.md |
|--------|------|---------|-----------|----------|
| 001-xxx | StopPatchServices 调整 | FR-035 更新 | 3.3.3 更新 | - |
| 001-xxx | RestoreWww 修复 | - | 3.4.3 更新 | - |

### 未处理条目

| 条目 | 原因 |
|------|------|
| xxx | 需求ID未知，需用户确认 |
```

---

## 四、注意事项

- **只读原则**: 仅更新文档内容，不修改代码
- **最小变更**: 只更新受影响的章节，不重写整个文档
- **版本历史**: 每次文档更新必须追加版本历史记录
- **格式一致**: 更新内容必须保持与文档原有格式一致
- **归档策略**: 已同步条目保留最近 30 条，超出归档
