## 二、执行流程

### 步骤 1: 加载上下文文档

| 文档类型 | 路径 | 说明 |
|----------|------|------|
| **项目规范** | `.windsurf/skills/project-context/SKILL.md` | 技术栈、编码规范、项目章程 |
| **功能规范** | `specs/[ID]/spec.md` | 用户故事、功能需求 |
| **开发设计** | `specs/[ID]/design.md` | 数据库设计、接口设计、功能流程、假设与前提、测试要点 |

> **重要**: 项目开发必须按照 `.windsurf/skills/project-context/` 目录下的 skill 文件规范实现。

### 步骤 2: 假设验证

读取 `specs/[ID]/design.md` 的 **1.4 假设与前提** 章节：

| 假设状态 | 处理方式 |
|----------|----------|
| ✅ 已验证 | 继续执行 |
| ⚠️ 待验证 | 提示用户确认或标记风险 |

将假设验证结果写入 tasks.md 的“假设验证检查点”章节。

### 步骤 3: 生成任务列表

**3.1 术语一致性检查**

在生成任务前，提取并统一术语：
- 从 spec.md 和 design.md 提取所有实体名称、接口名称、概念名称
- 检查是否存在术语漂移（同一概念在不同文件中命名不同）
- 如存在术语不一致，提示用户确认统一名称
- 将统一后的术语表写入 tasks.md 的“术语表”章节

**3.2 提取设计内容**

从 `specs/[ID]/design.md` 提取：
- **数据库表定义**: 逐表生成创建任务，表名必须与设计文档完全一致
- **接口设计**: 逐接口生成实现任务
- **功能流程**: 按设计流程生成实现任务
- **函数/方法代码示例**: 如果 design.md 包含函数代码示例，提取函数签名信息

**3.2.1 函数规格说明生成（如适用）**

如果 design.md 中包含函数/方法的代码示例，必须在基础阶段任务后添加「函数规格说明」章节：

```markdown
### 函数规格说明

**T00X FunctionName**
\`\`\`[language]
# 函数签名
FunctionName(param1, param2)
# 参数: $1 - 参数说明
# 返回: 返回值说明
# 行为: 函数的主要行为描述
# 错误码: EXXX 错误说明（如果有）
# 参考: design.md X.X.X FunctionName 函数
\`\`\`
```

生成规则：
1. 从 design.md 提取所有函数/方法的代码示例
2. 为每个函数生成规格说明，包含: 签名、参数、返回值、行为、错误码、参考位置
3. 将规格说明放在对应任务后面
4. 如果 design.md 包含错误码定义，在「代码规范引用」章节后添加「错误码定义」表

**3.3 按用户故事组织**

从 `specs/[ID]/spec.md` 提取用户故事（优先级1、优先级2、优先级3...），为每个故事生成：
- 数据模型任务
- 服务层任务
- 接口层任务
- 测试任务（可选）

**3.4 非功能需求覆盖**

从 `specs/[ID]/spec.md` 提取非功能需求，为每个非功能需求生成任务：
- **性能需求**: 生成性能优化/测试任务
- **安全需求**: 生成安全加固/审计任务
- **可用性需求**: 生成容错/恢复任务
- **可维护性需求**: 生成日志/监控任务

**3.5 验证任务完整性**

- 生成用户故事完成顺序的依赖关系图
- 为每个用户故事创建并行执行示例
- 验证每个用户故事都有所有必需任务，可独立测试
- **检查依赖关系冲突**: 验证任务排序无矛盾（如集成任务不应在基础任务之前）

### 步骤 4: 输出文件

读取 `.specify/templates/tasks-template.md` 模板，生成 `specs/[ID]/tasks.md`

### 步骤 5: 输出报告

输出 tasks.md 路径和摘要：
- 总任务数
- 每个用户故事的任务数
- 可并行执行的任务
- 每个故事的独立测试标准
- 建议的最小可行产品范围（通常只是用户故事 1）

任务生成上下文: $ARGUMENTS

> tasks.md 应该立即可执行 - 每个任务必须足够具体，以便可以在没有额外上下文的情况下完成。

## 四、任务格式规范

**关键**: 任务必须按用户故事组织，以实现独立的实现和测试。

**测试是可选的**: 仅当在功能规范中明确请求测试或用户请求测试驱动开发方法时才生成测试任务。

### 4.1 任务格式

每个任务必须严格遵循此格式:

```text
- [ ] [任务编号] [并行?] [故事?] 带文件路径的描述 | 验收标准 | FR-xxx
```

**格式组件**:

1. **复选框**: 始终以 `- [ ]` 开头（Markdown 复选框）
2. **任务编号**: 按执行顺序的序号（T001、T002、T003...）
3. **[并行] 标记**: 仅当任务可并行执行时添加（不同文件、无依赖关系）
4. **[用户故事] 标签**: 仅用户故事阶段的任务需要
   - 格式: [故事1]、[故事2]、[故事3] 等（对应 spec.md 中的用户故事）
   - 设置阶段: 无故事标签
   - 基础阶段: 无故事标签
   - 用户故事阶段: 必须有故事标签
   - 完善阶段: 无故事标签
5. **描述**: 带确切文件路径的清晰操作
6. **验收标准**: 可验证的完成条件（必须）
7. **设计追溯**: 关联的 FR-xxx 需求编号（功能任务必须）

### 4.2 禁止模糊描述

> **详细禁止词汇列表参见 `tasks-template.md` 中的“禁止模糊描述”章节**

基本原则：
- 禁止使用模糊词汇（快速、高效、可扩展、安全、健壮等）
- 禁止未解决的占位符（TODO、TKTK、???）
- 必须使用具体可验证的描述

**示例**:

- ✅ 正确: `- [ ] T001 根据实施计划创建项目结构`
- ✅ 正确: `- [ ] T005 [并行] 在 src/middleware/auth.py 中实现认证中间件`
- ✅ 正确: `- [ ] T012 [并行] [故事1] 在 src/models/user.py 中创建用户模型`
- ✅ 正确: `- [ ] T014 [故事1] 在 src/services/user_service.py 中实现用户服务`
- ❌ 错误: `- [ ] 创建用户模型`（缺少任务编号和故事标签）
- ❌ 错误: `T001 [故事1] 创建模型`（缺少复选框）
- ❌ 错误: `- [ ] [故事1] 创建用户模型`（缺少任务编号）
- ❌ 错误: `- [ ] T001 [故事1] 创建模型`（缺少文件路径）

## 五、任务组织规则

0. **来自设计文档(design.md)** - 强制提取:
   - **数据库表**: 逐表生成数据模型创建任务
     * 表名必须与 design.md 中定义的完全一致（不加前缀、不改名）
     * 字段类型、约束必须与设计一致
     * 示例: `- [ ] T010 [故事1] 在 models.py 中创建 job 表模型（design.md 4.1.1）`
   - **接口定义**: 逐接口生成实现任务
     * 接口路径、方法、参数必须与设计一致
     * 示例: `- [ ] T020 [故事1] 在 views.py 中实现 POST /job/user 接口（design.md 5.1）`
   - **功能流程**: 按设计流程生成实现任务
     * 流程步骤必须与设计一致
     * 示例: `- [ ] T030 [故事1] 实现用户导入作业运行流程（design.md 3.1.2）`

1. **来自用户故事(spec.md)** - 主要组织方式:
   - 每个用户故事（优先级1、优先级2、优先级3...）都有自己的阶段
   - 将所有相关组件映射到它们的故事:
     - 该故事所需的数据模型
     - 该故事所需的服务
     - 该故事所需的接口
     - 如果请求测试: 该故事特定的测试
   - 标记故事依赖关系（大多数故事应该是独立的）

2. **来自接口设计**:
   - 将每个接口端点 → 映射到它服务的用户故事
   - 如果请求测试: 每个接口 → 在该故事阶段的实现之前的接口测试任务 [并行]

3. **来自数据库设计**:
   - 将每个数据表映射到需要它的用户故事
   - 如果数据表服务多个故事: 放在最早的故事或设置阶段
   - 表关系 → 适当故事阶段的服务层任务

4. **来自设置/基础设施**:
   - 共享基础设施 → 设置阶段（阶段 1）
   - 基础/阻塞任务 → 基础阶段（阶段 2）
   - 故事特定的设置 → 在该故事的阶段内

4.5. **来自非功能需求(spec.md)** - 必须覆盖:
   - **性能需求**: 生成性能优化任务（如缓存、索引、异步处理）
   - **安全需求**: 生成安全加固任务（如输入校验、权限控制、审计日志）
   - **可用性需求**: 生成容错任务（如重试机制、降级策略）
   - **可维护性需求**: 生成监控任务（如日志记录、指标采集）
   - 示例: `- [ ] T050 [完善] 实现接口响应时间监控（NFR-001）`

5. **来自测试策略(design.md)** - 测试用例设计标准:
   - 读取 design.md 中的测试要点章节
   - **必须基于 design.md 生成测试任务**:
     * 从 design.md 数据库设计章节提取所有表 → 生成数据模型测试任务
     * 从 design.md 接口设计章节提取所有接口 → 生成接口测试任务
     * 从 design.md 功能流程章节提取所有流程 → 生成功能测试任务
   - 为每个用户故事生成完整的测试用例:

   **测试用例结构要求**:
   - **用例标题**: 【前置条件】+【操作场景】+【预期结果】
   - **前置条件**: 执行前的环境/数据/状态要求
   - **操作步骤**: 明确的操作序列
   - **预期结果**: 具体可验证的结果（界面变化、数据变化、状态变化）
   - **优先级**: P0(核心流程) / P1(主要功能) / P2(次要功能)

   **测试类型覆盖**:
   - **功能测试**: 正向流程 + 逆向流程 + 业务规则 + 数据验证
   - **接口测试**: 正常参数 + 边界参数 + 异常参数 + 幂等性验证
   - **边界值测试**: 最小值±1 / 最大值±1 / 空值 / 特殊字符
   - **异常场景**: 网络异常 / 服务异常 / 数据异常 / 操作异常

   **测试任务类型**:
     * **单元测试任务**: 每个新增/修改的模块 → 单元测试任务
     * **接口测试任务**: 每个接口端点 → 集成测试任务
     * **端到端测试任务**: 关键用户流程 → 端到端测试任务

   **测试任务放置规则**(层级测试模式):
     * 每层实施完成后立即跟随该层的测试任务
     * 测试通过后才能继续下一层
     * 示例: 数据层实施 → 数据层测试 → 逻辑层实施 → 逻辑层测试 → ...

   **测试任务格式示例**:
     * `- [ ] T015 [并行] [故事1] 在 tests/test_user_service.py 中为用户服务编写单元测试`
     * `- [ ] T020 [故事1] 在 tests/e2e/test_user_flow.py 中编写用户注册流程端到端测试`

## 六、阶段结构

- **阶段 1**: 设置(项目初始化)
- **阶段 2**: 基础(阻塞先决条件 - 必须在用户故事之前完成)
- **阶段 3+**: 按优先级顺序的用户故事（优先级1、优先级2、优先级3...）
  - **层级测试模式**（每层完成后立即测试验证）:
    ```
    数据层 → 数据层测试 → ✅检查点
         ↓
    逻辑层 → 逻辑层测试 → ✅检查点
         ↓
    接口层 → 接口层测试 → ✅检查点
         ↓
    集成验证 → 🎯故事完成
    ```
  - 每层测试通过后才能继续下一层，错误早发现
  - 每个阶段应该是一个完整的、可独立测试的增量
- **最终阶段**: 完善与横切关注点
  - 包含: 运行全部测试、检查覆盖率、性能优化、文档更新

### 7.1 章程符合性检查指导

读取 `.windsurf/skills/project-context/SKILL.md` 中的“项目章程”章节，验证：

1. **MUST 原则检查**: 每个任务是否符合章程中的 MUST 要求
2. **SHOULD 原则检查**: 每个任务是否符合章程中的 SHOULD 建议
3. **强制部分检查**: 章程中要求的强制部分是否都有对应任务

| 章程要求类型 | 检查方法 | 严重性 |
|----------------|----------|--------|
| MUST | 任务必须完全符合 | 严重 |
| SHOULD | 任务应该符合，不符合需说明原因 | 中 |
| MAY | 可选符合 | 低 |
